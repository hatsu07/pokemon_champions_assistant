# 構築別LIVEマトリクス／ルックアップとSingles環境データ

## 使い方

1. **設定 → 自軍構築** で現在ゲーム内で使う6匹と全4技、持ち物、特性、性格、能力配分を登録・保存。
2. **次戦に選択** → 設定画面下の **保存**。保存時に構築固有のマトリクス／60秒ルックアップをローカル作成・キャッシュする。
3. **対戦開始（4ファイル事前読込）**。選択構築、対応マトリクス、対応ルックアップ、共通LIVE判断ゲートの **4本文** をその試合で実読込・固定する。対戦開始後は再生成・Web参照しない。
4. 環境統計を新しくする場合のみ、**対戦前**に **シングル環境データを更新** を押す（バックグラウンド通信）。取得失敗なら前回の正常スナップショットを維持。 **ゲーム内統計JSONを取り込む** では同じJSONスキーマのプレイヤー確認情報を取り込む。
5. 勝敗が実画面で観測されると、必要最低限の試合記録を端末内に追記する。人間戦／CPU不明の推定や戦術評価の自動採用はしない。

## 「生成済み」と「実戦評価済み」は異なる

元のLIVEマトリクスは、2026-10-03構築の6匹専用に作られた358行の評価であり、異なる6匹に単純コピーできない。

- **REVIEWED_REUSE**：6枠とも元の評価対象と **同じポケモン・4技・持ち物・特性・性格・配分・関連状態** で一致した。順番違いは列を並べ替えて再利用できる。構築対応として扱い、元の戦術評価そのものが完全無欠であるという意味ではない。
- **PROVISIONAL_UNVERIFIED**：型の異なる枠は `?,?,?,?,U,0` として未検証、`??` で最初の行動を未確定とし、処理役／安全受けへ**昇格しない**。相手ポケモン358行・相手側の警戒候補は保持。データの構造は作成され、`matrix_compatible=false`と`live_ready=false`は維持する。ただし、生成器由来の構築別マトリクスで自軍6匹の順序が一致する場合、Champions事前確認データ・使用率候補からChatGPTが「暫定AI推奨」を選出・18対面PREP・各ターンに出すことを許可する。あくまで条件付き推論であり、確定KO・処理役・安全受けの検証完了や実戦READYとは表示しない。
- 明確な処理役、安全な受け先、新しい構築に対する高期待値の選出を評価するには、Champions専用の実際の検証済み対面データが別途必要。**公開の使用率統計から確1・受け安全・型確定を捏造しない。**

元の`masters/`は変更せず、プライベートの`<storage.data_root>/live-team-assets/<team_id>/<fingerprint>/matrix.txt`と`lookup.txt`、監査用`manifest.json`へ保存する。構築の実データ、元の両マスター、環境スナップショットのSHAに応じて別キャッシュへ保存し、同じ入力なら再利用する。各ファイルのSHAはmanifestにも記録。Gitや配布ZIPには同梱しない。

## Battle data 収集・更新と出典の扱い

- 公開SinglesのURL：`https://raw.githubusercontent.com/Gheist23/pokemonbattledata/main/data/builder/meta-singles.json`（`championsbattledata.com`の公開GitHubミラー）。
- 更新は利用者が明示的に「統計更新」または「構築別対面の自動解析」を開始した試合前に限る。8MiB上限、12秒タイムアウト、`format=Singles`、名称重複・順位・採用率の範囲を検証。
- `<storage.data_root>/battle-evidence/singles-usage.json` に統計本文、`singles-provenance.json`に**取得時刻・元データ生成時刻・出典URL・データSHA・単独/ダブル区分**を保存。公開元がレギュレーションを明記しない場合は `UNDECLARED_BY_SOURCE` とする。登録チームのレギュレーションを統計出典のレギュレーションと捏造して一致させない。
- 公開データとプレイヤー確認のゲーム内データは`source_kind`で区別。ゲーム内の最新情報が優先だが、データソースの更新・収集日も確認する必要がある。
- 勝敗確認後のみ`observed-matches.jsonl`へ1試合1行。これは**AIによる画面判定結果・未確認**という出典付きの自動収集であり、誤分類・CPU混入などを排除した正式統計ではない。技固定や安全受けの教師ラベルには自動昇格しない。
- 機械に存在するポケモン能力値・技定義・習得、持ち物、特性は別のChampions固定マスターが正本。使用率は相手の型確定ではない。SVやZAなど他作品で埋めない。

## 注意事項と未実装

**現在の仕組みは、元の構築と異なる型・ポケモンに対する対面評価の自動生成までは完成していません。** 正確な新規対面評価を作るためのChampions専用ダメージ検証、対面データのレビュー・承認UI、環境統計から試合状況別の対面処理役の確定は将来課題です。「構築を選択しただけで高勝率の完成マトリクスが得られる」という保証はありません。

外部サイトのschema/アクセスが変わる場合、更新に失敗しますが従来のマスターは破損しません。対戦中の通信・再学習は禁止。ダウンロード・マスター読込、キャッシュ生成は**次戦準備時**だけ。保存済みプライベートデータと元のLIVEマスターは上書きしません。


## 選出時の自軍正本と相手6匹の再認識（2026-10-25）

2026-10-25の実機ログでは、自軍に登録済みのドドゲザンが視覚モデルにより「ガオガエン」「Iron Valiant」と誤認され、`REGISTERED_TEAM_MISMATCH`で戦術モデル実行前に停止した。登録済みの自軍6匹は試合開始前の4ファイル事前ロードで凍結しているため、**選出画面で自軍6匹の名前を画像認識・再照合しない**。画面モデルの `our_six` は表示上の推測として扱わず空配列として破棄し、登録済み6匹が不正・重複の場合にのみ `REGISTERED_TEAM_INVALID` で停止する。

相手6匹だけを、選出画面全体と**相手右側の拡大クロップ**から認識する。モデルにゲームの画面ではなく登録済み自軍を推定させたり、候補順位・採用率から見えない相手を補完させたりしない。

初回の相手6匹に不足・重複・未確定位置・フォルム曖昧性・固定マスターに一致しない候補がある場合、**検証エラーと初回候補を「未確認」として添えた新しいChatGPT画像認識リクエストを1回だけ送る**。2回目の結果も必ず通常の相手6匹・フォーム・マトリクス存在チェックにかける。制限時間確保のため、戦術判断用に最低10秒を残せない場合は追加リクエストを省略し、不明として止める。3回以上の連続リトライはしない。これは信頼性向上策であり、画像認識の絶対的正確性や選出時間内の返答を保証するものではない。

2回でも認識不可の場合、モデルの推測で選出を出さず、`BLOCKED` と再認識回数を表示する。UIに選出結果を確定させず、元の登録自軍の技・持ち物・特性・APを使い続ける。対戦中のWeb検索・固定マスター再読込は禁止のまま。新しい画像に変化があれば次の通常の観測処理で再認識できる。


## 自動選出の遅延・SUPERSEDED 対策（2026-10-25）
実機ログで `AI_REQUEST_QUEUED #2` の応答が `66958 ms` を要し、送信中に新しいフレームをキューに入れたため、結果が `SUPERSEDED` として破棄された。未選出のまま制限時間を超える重大支援ミス。

- `MATCHMAKING / SELECTION` では、すでに `TEAM_SELECTION` の画像確認リクエストを実行中なら、同じ選出画面や未分類のアニメーション由来の追加フレームは送信キューに入れず、最初の選出推奨を優先する。
- 最初のリクエストが未分類 (`None`) の画面を確認中で、その後に明確な `TEAM_SELECTION` 検出があれば、新しい選出画像へ切り替えることを許す。選出推奨が正常に完了した時点で、未分類・同一選出画面由来のペンディングは破棄し、推奨自体は捨てない。新しい技・交代コマンド画面は従来どおり新しい状態を優先する。
- 選出時の画像観測は **相手6匹と画面判定の最小JSONスキーマ**を用い、既知の自軍6匹やHP・技・道具・対戦イベントの不要な生成を求めない。相手側画像はフルフレーム＋右側拡大1枚をモデルへ送る。
- 選出時のモデル推論はユーザー設定の高精度 `high` にかかわらず、**明示的な高速 `low`**を使用し、応答ログに `live_reasoning_effort` として記録する。バトル中の推論設定は従来の選択を保持する。
- 選出1回は認証・画面準備を含む共通35秒枠とし、画像認識に最大18秒、再認識に最大8秒、戦術判断に最大16秒の個別API通信タイムアウトを、残り時間より長くならないよう設定する。再認識には戦術用の18秒を温存する。**ストリーミングAPIのネットワーク・応答速度が遅い場合の実機35秒保証ではない**ため、実機の経過時間と `DEADLINE_EXCEEDED` を必ず記録する。
- 再度の支援では画像が不明な相手を捏造せず、事前ロードした固定データと現時点で確認できた6匹のみで推奨する。実機の90秒選出制限に間に合うかはBlueStacksの画像・通信環境で別途検証する。


## 統合済み: フェーズタイムアウト表示・自動診断ログ・試合外の選出画像テスト

旧 `fix/selection-phase-timeout-visibility` の変更は、`feat/automatic-match-debug-logs` に機能ごと統合済み。以後の開発・CI・PRは統合先の1本で行う。

- ゲームが選出画面に進んでもChatGPT応答が `ReadTimeout` になった場合、内部状態 `MATCHMAKING` を実画面だと断定しない。画面検出候補は `SELECTION候補（AI確認待ち）` と表示し、確定した相手6匹がない限り選出しない。タイムアウトした工程（相手画像認識・再認識・選出推論）を `request_stage` で記録する。
- 試合開始で `<data-root>/debug-logs/capture-<uuid>.jsonl` に自動追記。ログは形式 `champions-local-live-debug-v1`、各行にUTC・開始からのms・状態・AI通信経過・認識フェーズ・選出の成否などの許可項目だけを残す。**ChatGPT認証トークン、画像、モデル入力、自由文のAPIレスポンス、構築の秘密情報は含めない。** 最新20セッション、ファイルあたり約3MiBに制限し、保存失敗で対戦支援を停止しない。
- メイン画面の **「選出画面テスト（試合外）」** から、PNG/JPEG画像をファイルで指定し、選択中の登録構築の4ファイルを試合前にロード。実戦と共通の `run_replay_image` で「相手6匹→自軍3匹＋初手」を1回実測する。35秒の同じ処理上限を渡し、認識回数・状態・所要時間・選出・失敗理由をUIへ表示し自動診断ログへ保存する。試合外のみ利用可能で、ゲームの自動操作・キャプチャはしない。画像ファイルはログへコピー・保存しない。
- オフラインCIの模擬成功は、**実機の画像認識精度、実ChatGPTの通信成功率、時間内選出、対戦勝率の保証ではない**。実際の選出画像と最新ログを使い、モデルとのE2Eを別途検証する。


## 実機オフライン選出テスト 2026-10-25 21:38 JST: 相手認識初回 ReadTimeout
ユーザー提供の開発版 dev.22 `capture-7561bb2a4d39458bb65f0254cd8e58c9.jsonl` で、選出画面PNG/JPEGは正常にロードしたが、`gpt-5.6-terra` による **`OPPONENT_VISUAL_RECOGNITION` 初回通信**が約23.24秒経過後に `ReadTimeout`。相手6匹と3匹選出は共に未実行。これは認識内容の不一致やLIVEマトリクス不備でなく、少なくとも画像モデル応答を受信できなかった通信失敗。モデル負荷・ネットワーク・API混雑の内訳はこのログ単体からは断定できない。

対策（試合外テストと本番選出で同じ `run_replay_image` を使用）：
- 4ファイル事前ロード・登録済み自軍6匹を正本に維持しつつ、初回の相手画像認識はフル画面＋相手側2画像から、**右側相手6匹の高精細クロップ1画像**に変更。画面サイズ・向きが異常なら全体1画像に戻す。精度が不足した時の検証リトライでは、文脈用にフル画面 `low` と相手クロップ `high` を提供する。
- 最初の相手画像認識を12秒で区切る。**ネットワーク `ReadTimeout` 等で内容を一切受信できなかった場合**、35秒の共通選出枠に16秒超の余裕があれば、相手専用画像を再送信（通信最大7秒・1回のみ）。それ以外は中断。曖昧な6匹に対する検証リトライと通信リトライを重ねて3回以上送信しない。選出AI判断に時間を残し、推測で6匹を補完しない。
- 診断ログへ `visual_first_attempt_elapsed_ms`、`visual_transport_retry_elapsed_ms`、`visual_image_count`、`request_stage`、`opponent_recognition_attempts` を保存。個人の画像、OAuth、自由文APIレスポンスは保存しない。
- **未実施：実ChatGPTとの通信成功率・応答時間、BlueStacks実戦で90秒内に選出できるか、右クロップ1枚による6匹の認識精度。** Windows CIの模擬APIテストはこれらの代用ではない。根本原因がネットワーク/サーバー応答であれば、画像削減で解消する保証はない。
