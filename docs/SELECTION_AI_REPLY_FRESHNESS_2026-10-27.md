# 選出AI：選出優先・回答の鮮度・遅延時の扱い（2026-10-27）

## 実機ログで確認した失敗
- 2026-10-27のユーザー提供ローカル診断では、ONNX分類器は選出画面を信頼度1.0で認識し、AI画像リクエストを1回開始した。
- 認証約2.0秒、合計約61秒後に `DEADLINE_EXCEEDED` となり、選出は表示されなかった。応答処理終了時点でも画面分類は `TEAM_SELECTION` だった。PREPは開始されていない。
- 旧コードは有効な選出が生成できても、55秒を超えれば `SelectionPlanner.choose` と `run_replay_image` の両方で破棄し得た。タイムアウトと失敗は区別する必要がある。

## 応答の優先順位と有効性
1. 選出リクエストでは `selected_three` 3匹と `lead` のみを必須とする。登録済み構築か検証し、まず画面表示する。選出前に温存・ストッパー・締め役を必須にしない。
2. PREPは**選出表示後**に開始する。既存の凍結マトリクスから18対面の基礎を組み、必要な勝ち筋3点を別の段階で求める。選出表示をPREPの終了まで待たせない。
3. 55秒は応答時間の目標／新規処理の時間配分であり、ローカル時計だけで**取得済みの検証済み回答を破棄しない**。遅延は記録する。
4. 新しい **操作判断のAI依頼が待機**したとき、未回答の古い結果は無効化する。重複した同一選出画面・アニメーションや未分類画面だけでは前の応答を消さない。
5. 画面が別種に変わったが新しい操作判断がまだ待機していない場合、完成した選出候補は診断・参考として表示する。ただし画面の継続が未確認なので選出を自動的に採用せずPREPも開始しない。
6. 戦闘ターンで新ターン／技の実行イベントが確定した場合は前ターンの行動提案を現行アクションとして表示しない。通信自体がタイムアウトし完了JSONが届いていなければ有効な行動は捏造しない。
7. 手動の停止／キャンセルは最優先。過去の完了回答は履歴に残っていても現在の選出・行動として再利用しない。

## 実装確認
- 画像認識と選出判断の時間はそれぞれ `selection_visual_ms` と `selection_tactical_ms` として、個人データを含めずローカルデバッグログに記録する。
- オフライン回帰テストは、有効選出が55秒超でも保持されること、現行選出画面ではまず表示してからPREPに入ること、新しい判断が待機したとき古い未着回答を抑止すること、画面が変わっただけなら参考表示に留めることを検査する。
- Windows CI / オフライン検証とBlueStacks実機の応答時間・選出UIタイマーの検証は別工程。CI通過だけで実機の改善を断定しない。
